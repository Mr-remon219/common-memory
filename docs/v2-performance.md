# V2 实现性能优化

## 结果与范围

保留五种触发和全部默认参数，仅修改 `src/v2/runtime.ts` 的 SQLite 访问路径。
真实模型、Prompt、Markdown/回执协议、Writer、Pi 来源判断均未修改。无新依赖或正文 schema 迁移。

本机配对微基准：

| 场景 | 修改前 median（ms） | 修改后 median（ms） | 修改后 P95（ms） | 前/后耗时比 |
|---|---:|---:|---:|---:|
| 空闲检查：20 条历史 | 0.018 | 0.024 | 0.036 | 0.77× |
| 空闲检查：20,000 条历史 | 6.942 | 0.032 | 0.045 | 214.00× |
| 强制领取：6 条待处理 | 0.096 | 0.159 | 0.187 | 0.60× |
| 自动领取：2,000 条积压 | 10.998 | 0.207 | 0.259 | 53.19× |
| 首次打开旧库：20,000 条历史 | 0.304 | 11.119 | 13.143 | 0.03× |
| 强制领取：2,000 条积压 | 12.419 | 0.241 | 0.331 | 51.48× |
| 重复恢复：2 份已确认回执 | 0.321 | 0.345 | 0.568 | 0.93× |
| 重复恢复：500 份已确认回执 | 16.893 | 17.998 | 20.593 | 0.94× |

比例大于 1 表示加快，小于 1 表示变慢。这里的比值是**SQLite/文件系统局部操作**，
不是端到端模型延迟、Token 成本或线上吞吐提升。

## 修改

1. 新增 `observations(state,id)`、非空 `jobId`、活跃 job 部分索引，避免历史记录拖慢队列查询。
2. 已处理正文清理增加 `text IS NOT NULL`，避免反复 UPDATE 已清空正文；配合只索引尚有正文的部分索引。
3. EXPLAIN 发现 SQLite 原先偏好 state 索引、仍扫描全部 processed；此条 UPDATE 现在显式指定 `observations_prunable`。
4. claim 只解码本批容量的队首，不再把全部待处理正文复制到 JavaScript。
5. 数量仍对全 pending 跨 Scope 判断；必要时用 SQLite UTF-8 BLOB 字节总和判断体积。
6. 首尾时间仍按 Entry 入队 ID 选取，不改成时间 MIN/MAX；领取后检查剩余 pending 保留 flush 尾批。

不缓存队列计数、不跳过 lease/CAS/权限/恢复校验。永久回执读取未优化，其波动不计作收益。

## 代价与限制

- 小库空闲检查约增加 **0.005 ms**，小批领取约增加 **0.063 ms**。新增索引维护和查询有固定成本，不隐瞒这个退化。
- 首次打开现有 20k 历史库建索引，本机约增加 **10.8 ms**；之后重开不重复重建。
- 索引占用额外空间并增加写入维护；本轮未测磁盘容量增长或大规模持续写入吞吐。
- 500 份永久回执重复恢复仍约 18 ms，线性扫描风险未解决。为保留恢复/隐私保证，本轮没有以跳过确认回执验证换取速度。
- 自动领取场景满足数量触发；不代表所有“未达到阈值”的小队列路径都同样加快。
- 微基准样本为本地合成数据，9 个样本的 nearest-rank P95 等于最大样本，不是生产 P95 估计或统计显著性证明。

## 方法

- 修改前先构建并冻结完整 dist，随后再修改实现。基线源码摘要与完整编译树 manifest 保存在结果 JSON。
- 每场景 2 次 warmup、9 个正式样本；基线/候选交替顺序，使用独立临时 dataRoot。
- 造数不计时。空闲场景 20k processed body 已为 NULL；积压场景 2k × 4 KiB 完整 Turn，另含 20k 已完成 jobs。
- 领取在外层事务中回滚，从同一初始队列反复测量；每次检查准确的前 6 个 ID、完整正文及剩余队列。
- 除“首次打开旧库”外，构造器和建索引不计时；首次打开病例用旧实现建库，再计时新实现的第一次构造。
- 恢复测量 constructor 之后的重复恢复，不是冷启动。模型 stub 在被调用时直接失败，实际网络调用为 0。
- 环境：Node v24.16.0，linux / x64，AMD Ryzen 7 7800X3D 8-Core Processor。完整 OS、样本与摘要见 [配对结果](v2-performance-results.json)。
